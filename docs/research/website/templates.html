Shared shell

One header on every page. Search opens with / or Ctrl K and searches titles, headings, props, parts and token names from a static index built at build time. The framework choice (HTML, Elements, React) is set once and remembered on every page. Vue, Svelte and Angular users get a guide to Elements, not their own tabs. Theme and mode switch the whole site, because the site is styled only by Saral.

Getting started

The benchmark's fastest systems (GOV.UK's prototype kit aside, Ark and plain CDN routes) reach a working component in under five minutes; the slowest need a CSS engine and code generation first. Saral can beat all of them with one HTML file. The page offers three paths, each three steps or fewer, and ends with a complete file you can paste and open.

Component page

One long page, not tabs, so everything is findable with search and Ctrl F, and works with JavaScript off. Order follows what a reader needs first: see it, decide if it fits, copy it, then the contract (Ark's parts and data-attribute tables, Chakra's highlight-on-hover anatomy), then accessibility with a testing table tied to a version (Carbon) and writing guidance (Stripe, Fluent), and last the record of how the component got here (GOV.UK's research, known issues, recent changes and help-improve sections). Every section is generated from specs/*.json, so the page cannot drift from the code.

Tokens

Token pages fail in two ways in the benchmark: you cannot find the name you need, and you cannot see what a role is for. Saral's page is a filterable table of roles with the job of each role in one line (Geist gives every colour step a job), live swatches in the current theme and mode, and every contrast pair with its measured ratio, generated by the same code that gates the build.

Themes

A theme is Saral's main promise, so it gets its own section. Before the theme builder ships (M5), the page shows the themes and a written guide; after, the builder takes one brand colour, fills every role, runs Saral's own contrast checks in the browser and exports DTCG and CSS. Park UI's accent and grey picker and Linear's three-input theme model are the references.

Playground

Most systems send readers to StackBlitz or CodeSandbox, which is slow and needs an account to save. Saral's components are HTML, so the playground can run in the page with no server: an editor, a preview frame, and the state kept in the URL so every share link works offline from the site.

Rules for every template

  1. Every page reads in full with JavaScript off. Search, the playground and remembered choices are the only parts that need it.
  2. Every page is styled only by Saral tokens and components. If the site needs something Saral lacks, that is a gap in Saral.
  3. Every page has a Markdown twin at the same path, listed in llms.txt.
  4. Page weight budget: 150 kB on first load including fonts; under 15 kB of JavaScript outside the playground.
  5. axe clean in every theme and mode, checked in CI on every page.
