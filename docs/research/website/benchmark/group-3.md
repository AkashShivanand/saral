# Group 3 benchmark: GOV.UK, Carbon, Polaris, Primer, Atlassian

Researched on 13 October 2026 with web search and page fetches only (no browser). Scores run 1 to 5, where 5 is best in class. For criterion 10, a higher score means fewer and milder complaints. Where a page could not be fetched or a detail could not be confirmed, the evidence says so.

**Research evidence, status and backlog.**
- Research: an H2 "Research on this component" on each page, written as a short narrative (what was tested, with whom, what changed), linking to the GitHub discussion for detail. The Feedback component explains the hypothesis its trial is testing. No sample sizes or methods on the page.
- Status: only two statuses, Trial and Stable. Trial shows a tag and a one-line message; Stable shows nothing. A trial becomes stable after six months with no negative feedback. The brief's "Experimental" label is no longer used. https://design-system.service.gov.uk/community/component-lifecycle-statuses/
- Backlog: "Upcoming components and patterns" lists Working on now, Next priorities and the essential-component criteria, each item linked to a GitHub discussion; the long tail is a GitHub discussion category, "community-backlog". Every component page ends with "Help improve this component", which points to the same discussion. https://design-system.service.gov.uk/community/upcoming-components-patterns/

**Home page structure.** Cookie banner, skip link, header (logo, search, sitemap, menu), six-item nav, hero ("Design your service using GOV.UK styles, components and patterns", Get started), What's new (latest Frontend release with links), Get updates (email), three cards for Styles, Components and Patterns, refreshed brand notice, Principles we follow, Community, Support, Roadmap, footer.

**Steal.** The fixed component page order, ending with Research, Known issues and gaps, Recent changes and Help improve this component. Saral already writes decision and incident records; link each component page to its records and its open questions in the same fixed slots.

**Avoid.** Leaving assistive technology results in blog posts and discussions. Put a dated, per-component test table (screen reader, browser, result, known bugs) on the page itself.

## Cross-system summary

GOV.UK is the model for honest, evidence-led component pages: a fixed section order that ends with research, known issues, dated changes and a link to the open discussion, and a two-state lifecycle that is easy to read. Its gaps are tools (no editable examples, no theming), and its assistive technology results sit in blogs rather than on component pages. Carbon and Primer lead on per-component accessibility tabs, with Carbon's versioned testing status table the strongest single artefact in this group, and Primer leads on live code (editable examples with reset and StackBlitz) and per-platform status labels. Atlassian leads on token lookup and on machine access (CLI and MCP that mirror the site) but has the heaviest setup and JavaScript-dependent pages. Polaris is the warning: deprecating the React library, redirecting every old deep link to one index page and shipping thinner docs for the new web components produced the worst complaints in the group. For Saral the pattern to copy is GOV.UK's page order filled with Carbon-style generated test evidence, Primer-style adapter status, and Atlassian-style token lookup, all served as static HTML, with stable URLs that never silently redirect.
