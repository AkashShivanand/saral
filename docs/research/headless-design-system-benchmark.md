# Saral wins by compiling contracts, not components

A headless design system keeps behaviour, state and accessibility in a core that renders little or no styling, and lets a separate, swappable theme decide how everything looks. By late 2026 the leading headless libraries (React Aria, Base UI, Headless UI, Zag/Ark) have settled on the same contract: named parts, interaction state exposed as normalised `data-*` attributes, geometry passed as CSS variables, and an explicit composition hook. The big systems' documented failures cluster in five places. Their styling engine was part of the public API (MUI, Chakra, Primer, styled-components). Their major versions shipped without parity or codemods (Fluent, Chakra, Tailwind v4, Polaris). They shipped an attractive default that failed accessibility and fixed it with a user toggle (Apple's Liquid Glass). Figma kits and docs drifted from code. And their maintainers left or were de-staffed (Radix, Material Web, MUI, Tailwind Labs). The systems that evolve fastest without breaking anyone do it with additive minor releases, an explicit preview lane, deprecations enforced by lint rules and codemods, and, as of 2026, a machine-readable interface compiled from the same source as the human docs: 18 of 21 major systems now ship an official MCP server. Most of Saral's decisions hold up against this evidence. Three need adjusting. Build the v1 kit on native HTML elements and keep the state machines small, mainly as a portable spec. Label the Swift, Compose and Figma token outputs "preview" until something consumes them. And prototype the Anek width axis on iOS and Android before promising it, because no token format, and no confirmed native API for a custom font, carries it cleanly. One maintainer cannot be the fastest system by release count or breadth. He can be the fastest at turning a mistake into a rule that cannot be broken again, and that is where Saral can set a benchmark.

## Headless has converged on one contract: parts, data attributes, CSS variables

The idea is older than the word. Martin Fowler's site published Juntao Qiu's definition in November 2023: a headless component is "responsible solely for logic and state management without prescribing any specific UI", which lets the logic be reused under different visuals and tested without rendering. The same article warns that the extra abstraction "can reduce readability if applied without restraint" ([Fowler/Qiu](https://martinfowler.com/articles/headless-component.html)). The pattern spread from Kent C. Dodds' Downshift at PayPal in 2017, which rendered no markup and only exposed state and an API ([SD Times](https://sdtimes.com/github/sd-times-github-project-week-downshift/)). Tanner Linsley says Downshift pushed him to rewrite React Table to "invert control" ([GitNation](https://portal.gitnation.org/contents/5-years-of-building-react-table)). Nobody in the research could find who coined "headless" for UI. In practice the ecosystem has split into three layers. Logic-only hooks or machines (Downshift, React Aria hooks, Zag) sit at the bottom. Unstyled primitives that render accessible markup sit in the middle (Radix, Base UI, Ark). Styled kits sit on top (shadcn/ui, which since July 2026 defaults new projects to Base UI instead of Radix) ([releases.sh](https://releases.sh/release/rel_TUxVOyVHeyyTBGlCTm6n4)). Saral's machine, adapter and CSS theme map exactly onto those three layers, which is the first sign the architecture is sound.

The convergence on a styling contract is striking. React Aria Components expose pressed, hovered and selected as data attributes that "work consistently between mouse, touch, and keyboard modalities", accept `className` and `style` as functions of state, use predictable default class names so plain CSS works, and pass geometry such as `--trigger-width` as CSS variables ([React Aria styling](https://react-aria.adobe.com/styling)). Base UI does the same with `data-checked`, `data-highlighted` and `data-pressed`, adds **`data-starting-style` and `data-ending-style` so pure CSS can animate mount and unmount**, and passes `--available-height` and `--anchor-width` ([Base UI styling](https://base-ui.com/react/handbook/styling)). Headless UI v2 (May 2024) made the key point explicit: its `data-*` attributes "behave more consistently across different devices than the native CSS pseudo-classes". `data-hover` is ignored on touch to avoid sticky hover, `data-active` is removed when a finger drags off, and `data-focus` behaves like `:focus-visible` "without false positives from imperative focusing" ([Headless UI v2](https://tailwindcss.com/blog/headless-ui-v2)). React Aria's post on building a button explains why even the simplest control is hard: browsers emulate mouse events on touch, `:hover` and `:active` get stuck, and touch cancellation needs handling ([React Aria: Building a Button](https://react-aria.adobe.com/blog/building-a-button-part-1)). The lesson for Saral's CSS-first theme is direct. The attributes must be **normalised by the behaviour layer, not mirrored from pseudo-classes**, or the theme inherits every browser quirk.

Where the libraries differ is where behaviour lives. React Aria keeps it in React hooks, Radix and Base UI keep it in per-component React state, and Zag keeps it in framework-agnostic statecharts with thin adapters. Zag's founding rationale is the closest prior art to Saral. Chakra kept hitting bugs from orchestrating events and side effects inside `useEffect`, `useMemo` and `useCallback`, the same bugs reappeared in the Vue port, and so the team modelled each widget once as a machine and wrote adapters for React, Solid, Vue and Svelte ([Zag introduction](https://zagjs.com/overview/introduction)). Ark UI now ships 45+ components with one API across four frameworks on that layer ([Ark UI](https://ark-ui.com/)). That is strong evidence that machine plus thin adapter works. The counterweight is that **behaviour is more than a state machine**. Headless UI v2 did not write its own interaction layer: it composes React Aria hooks for press and hover, Floating UI for positioning and TanStack Virtual for long lists ([Headless UI v2](https://tailwindcss.com/blog/headless-ui-v2)). Mature systems borrow these sub-libraries rather than rebuild them.

The headless layer has its own documented failures, and they are instructive. Radix's maintainers largely left after the WorkOS acquisition, and shadcn/ui, the largest styled layer built on it, changed its default foundation as a result ([DEV](https://dev.to/mashuktamim/is-your-shadcn-ui-project-at-risk-a-deep-dive-into-radixs-future-45ei); [shadcn-ui#1622](https://github.com/shadcn-ui/ui/issues/1622)). Some still argue Radix is "feature complete" rather than abandoned, and its repo showed commits in October 2026 ([Radix primitives](https://github.com/radix-ui/primitives)). Implicit composition through `asChild` and Slot loses styles with multiple children ([DEV](https://dev.to/weamadel/fixing-shadcn-slot-issues-with-multiple-children-n2)) and leaks props to the DOM when the underlying primitive changes ([shadcn-ui#10465](https://github.com/shadcn-ui/ui/issues/10465)). Base UI replaced it with a `render` prop whose contract is explicit: the target "must forward the `ref`, and spread all the received props" ([Base UI composition](https://base-ui.com/react/handbook/composition)). JavaScript-managed global side effects are the most fragile area of all. A Radix modal menu that unmounts mid-animation can leave `body { pointer-events: none }` behind and freeze the page (radix-ui/primitives#3445, via [a downstream fix](https://git.laurivan.com/Mirrors/blakeblackshear.frigate/commit/d8f70b7fedd23cbc2f0bf4054a7b8adee1da2726)). Complex widgets such as combobox and multi-select are where under-maintained libraries lag most ([shadcndeck, opinion](https://www.shadcndeck.com/blog/radix-vs-base-ui)).

One significant gap in the evidence matters for Saral. The research found **no primary source evaluating web components as the carrier for a headless system**, nothing on ARIA references across shadow roots, and nothing on server-rendering custom elements. Shopify did move Polaris extensions to `s-*` web components and cut bundles by 40 to 85%, but at the cost of missing components and an unversioned CDN script that consumers cannot pin ([InfoQ](https://infoq.com/news/2026/10/shopify-web-components); [Shopify forum](https://community.shopify.dev/t/is-anyone-else-disappointed-with-polaris-web-components-so-many-missing-features/23687)). Saral's chosen route, light-DOM elements styled by data attributes with a thin React adapter, avoids that unresearched risk. That is a point in favour of the decision as made.

## One DTCG source compiles to every platform, but Figma and native lose data on the way

Design tokens began at Salesforce, where the Theo tool converted one JSON file into Sass, Less, iOS and Android formats as early as 2015 ([Jina Anne deck](https://speakerdeck.com/jina/lightning-design-system)). The format finally stabilised a decade later. DTCG 2025.10 shipped on 28 October 2025 as a "production-ready, vendor-neutral format" with theming, OKLCH and Display P3 colour, aliases and inheritance ([W3C DTCG](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)). It is a Final Community Group Report, **not on the W3C Standards Track** ([designtokens.org](https://www.designtokens.org/tr/2025.10/)), and its two founding co-chairs stepped back in June 2026 with no roadmap or date for a next version ([W3C DTCG](https://www.w3.org/community/design-tokens/2026/06/17/thank-you-jina-and-val/)). The Resolver module models light and dark as whole alternative files selected by a `theme` modifier, not as per-token mode maps ([DTCG Resolver](https://www.designtokens.org/tr/2025.10/resolver/)).

Tooling is behind the spec. Style Dictionary's own docs say 2025.10 is "not fully supported yet". Its tracking issue was still open on 9 October 2026, with the resolver at the discussion stage, and a maintainer said he lacked capacity to lead the work ([Style Dictionary #1590](https://github.com/style-dictionary/style-dictionary/issues/1590)). Terrazzo 2.x claims full 2025.10 support including resolvers, but offers no Android or Compose output ([Terrazzo](https://terrazzo.app/docs/integrations/swift/)). **This evidence supports Saral's decision to write its own build script.** The cost is that Saral must own alias resolution, cycle detection and JSON Pointer `$ref` handling, all of which the spec mandates ([DTCG Format](https://www.designtokens.org/tr/2025.10/format/)).

Figma is the leakiest target. Native import accepts colour only in sRGB or HSL, dimensions only in px and durations only in seconds. It holds no composite types such as typography or shadow, and **creates a variable only if the token exists in every mode file with the same type**, so a token missing from dark mode silently disappears ([Figma Help](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)). In April 2026 a user reported that re-importing a native export brought back 2 of 256 variables ([Figma forum](https://forum.figma.com/report-a-problem-6/variable-export-import-broken-53229)). The consistent conclusion is that Figma should be an output and never a source. Saral's "Figma mirror generated from code" is the right call.

Every major system uses three tiers under different names: Material's ref/sys/comp, Primer's base/functional/component, Fluent's global/alias ([material-web.dev](https://material-web.dev/theming/material-theming/); [Primer token names](https://primer.style/product/primitives/token-names/); [Fluent 2](https://fluent2.microsoft.design/design-tokens)). **The semantic middle tier is what carries the system.** Without it, three menus end up with three hover colours and no principled answer for a fourth ([Design Systems Collective](https://www.designsystemscollective.com/a-token-story-part-1-51ac3df380db)). Some teams have dropped the component tier entirely as a maintenance burden ([ZCOOL](https://www.zcool.com.cn/work/ZNzA4NzExODA=.html)). Scale is real: Adobe Spectrum's data set holds 2,338 tokens across 8 files ([Spectrum discussion #646](https://github.com/adobe/spectrum-design-data/discussions/646)). Primer's rule that the property is the only required part of a token name keeps names short ([Primer](https://primer.style/product/primitives/token-names/)). For lifecycle, Atlassian runs tokens through active, deprecated, soft-deleted (still works, raises errors) and removed stages, with lint auto-fix and codemods ([Atlassian](https://atlassian.design/foundations/tokens/use-tokens-in-code)). Spectrum keeps deprecated tokens for at least two minor versions and requires a replacement mapping ([Spectrum evolution spec](https://opensource.adobe.com/spectrum-design-data/spec/evolution)).

On colour, OKLCH is the right authoring space because its perceptual lightness keeps contrast predictable across hues. Two caveats apply: Chrome and Safari clip out-of-gamut colours instead of mapping them, and Figma has no official OKLCH support ([Evil Martians](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl)). The contrast gate should stay on **WCAG 2.x ratios**. APCA was pulled from the WCAG 3 draft, whose contrast method was still "yet to be determined" in 2026 ([Adrian Roselli](https://adrianroselli.com/2026/04/wcag3-contrast-as-of-april-2026.html)), and W3C says WCAG 3 will not supersede WCAG 2 ([W3C WAI](https://www.w3.org/WAI/news/2026-03-03/wcag3)). Radix's 12-step scale is a usable model: each step has a job, and steps 11 and 12 are guaranteed text contrast on step 2 ([Radix Colors](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)). Apple asset catalogs hold four variants per colour (light, dark, and high-contrast versions of each), and Fluent ships high-contrast themes, so a third resolver context is cheap and expected ([Swiftjectivec](https://www.swiftjectivec.com/one-color-becomes-four); [Fluent 2](https://fluent2.microsoft.design/design-tokens)).

Typography and motion are where Saral's brand outruns the standard. DTCG's typography composite has **no field for font-variation axes**, and its fitness is an open issue (#102) ([DTCG Format](https://www.designtokens.org/tr/2025.10/format/)). On Android, Compose supports `FontVariation.width(...)`, but only on API 26 and above and **not for downloadable fonts**, so the variable file must be bundled ([Android Developers](https://developer.android.com/develop/ui/compose/text/fonts)). On iOS, Dynamic Type scaling of custom fonts is well documented ([WWDC20 notes](https://wwdcnotes.com/notes/wwdc20/10175)), but the research **could not confirm from Apple docs** that an arbitrary width axis can be set on a custom font. Fluid `clamp()` type can fail WCAG 1.4.4's 200% resize unless the preferred value includes a rem term and the maximum is checked under zoom ([Roselli](https://adrianroselli.com/2019/12/responsive-type-and-zoom.html); [Smashing](https://smashingmagazine.com/2023/11/addressing-accessibility-concerns-fluid-type)). Motion has the same gap. DTCG covers only duration, cubic Bézier and transition, while Material 3 Expressive moved Compose to spring-based motion schemes ([composables.com](https://composables.com/docs/androidx.compose.material3/material3/interfaces/MotionScheme)). Both need Saral's own `$extensions`, which spec-compliant tools must preserve ([DTCG Format](https://www.designtokens.org/tr/2025.10/format/)).

The broader lesson about "platform-agnostic" is that what crosses platforms in practice is the **spec and the tokens, not the runtime**. Material's own web implementation never supported its ref-palette or shape tokens ([material-web.dev](https://material-web.dev/theming/material-theming/)), which shows how a system's spec and one platform's implementation drift apart. SwiftUI and Compose already separate behaviour from appearance natively, so a sensible inference is that Saral's native ports should reuse platform behaviour and port only the state and event spec, the part names and the tokens. Running the TypeScript machines on device would be the wrong move.

Read across the rows and five root causes repeat. The first and most expensive is **a styling engine or rendering framework underneath a stable-looking component API**. styled-components went into maintenance mode in March 2025 because it cannot work with React Server Components without `'use client'` ([styled-components #5657](https://github.com/orgs/styled-components/discussions/5657)). MUI's zero-runtime replacement stalled ([MUI 2026](https://mui.com/blog/2026-and-beyond/)). Primer moved to CSS Modules ([primer #7086](https://github.com/primer/react/discussions/7086)), and Chakra dropped Emotion and framer-motion ([Chakra](https://next.chakra-ui.com/docs/get-started/migration)). Every one of those consumers paid for a change they did not ask for. A system whose public contract is tokens, DOM and ARIA anatomy, and CSS custom properties is insulated from that churn by construction. This is the strongest single argument for Saral's CSS-first decision.

The second cause is **migration without parity, codemods or honest status**. Fluent shipped v9 without v8's components and told customers "we don't intend to shim every component" ([fluentui #23183](https://github.com/microsoft/fluentui/discussions/23183)). Chakra's migration guide called itself "a work in progress" at release. MUI admitted in 2026 that "it's not enough to quietly shift priorities" ([MUI](https://mui.com/blog/2026-and-beyond/)). A new cost has appeared on top of the old ones: **AI assistants keep emitting the old API after a breaking rename**, so consumers pay once in code and again in every agent ([Cursor forum](https://forum.cursor.com/t/using-a-new-version-of-a-library-with-a-breaking-change/51217)).

The third is **override pain from a narrow theming surface**. Styling and customisation was the top component-library pain point in State of React 2024, which the report ties to the rise of headless libraries ([State of React 2024](https://state-of-react-2024.onrender.com/zh-Hans/libraries/component-libraries)). Salesforce now has to tell teams not to depend on internal markup ([Salesforce](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-css-slds1-slds2.html)), and Primer added stable `data-component` attributes because consumers' tests and overrides were relying on CSS Module hashes that "break silently when Primer is updated" ([Primer ADR-023](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-023-stable-selectors-api.md)).

The fourth is **an attractive default that fails people**. NN/g's October 2025 review of Liquid Glass documented low contrast over photos, text sitting on text, unrequested motion and smaller controls ("Motion for motion's sake is not usability") ([NN/g](https://www.nngroup.com/articles/liquid-glass/)). Beta testing measured some screens near 1.5:1 against WCAG's 4.5:1 ([Infinum](https://infinum.com/blog/apples-ios-26-liquid-glass-sleek-shiny-and-questionably-accessible/)). Apple's fix was a Clear or Tinted user setting in iOS 26.1, not a better default ([9to5Mac](https://9to5mac.com/2025/10/20/ios-26-1-beta-4-adds-new-setting-to-tone-down-liquid-glass-transparency/)). Sameness is the quieter version of the same failure. A computer-vision study of about 200,000 page images found web layouts became more than 30% more similar after 2007, and the designers interviewed blamed shared libraries and standardised colour schemes ([CHI 2021](https://vision.soic.indiana.edu/papers/websimilarity2021chi.pdf)). In 2025 to 2026 the effect compounded because v0, Bolt and Lovable all build on shadcn ([RedMonk](https://redmonk.com/kholterhoff/2025/04/22/ui-component-libraries-shadcn-ui-and-the-revenge-of-copypasta/)), and v0 is "specifically trained on the default implementations" ([v0 docs](https://v0.app/docs/design-systems)).

The fifth is **people**. Adoption has been a top-three challenge since Sparkbox's 2021 survey ([Sparkbox](https://designsystemssurvey.seesparkbox.com/2021)). zeroheight's 2026 report says the "resource crisis is accelerating" and names documentation as "both the biggest pain point and the clearest opportunity" ([zeroheight 2026](https://webinars.zeroheight.com/watch/zeroheight-design-systems-report-2026-the-findings)). It also relays that 59% of practitioners see AI-generated UI bypassing their system ([report.zeroheight.com](https://report.zeroheight.com)). Google de-staffed Material Web, Tailwind Labs lost three of four engineers, and the 18F team behind USWDS was eliminated ([9to5Google](https://9to5google.com/2024/06/25/material-web-components/); [DevClass](https://www.devclass.com/2026/01/08/tailwind-labs-lays-off-75-percent-of-its-engineers-thanks-to-brutal-impact-of-ai/); [Brad Frost](https://bradfrost.com/links/post/18f-we-are-dedicated-to-the-american-public-and-were-not-done-yet/)). For a one-person system this is not background colour. It is the main risk, and it argues for the smallest surface that can be maintained alone.

## The fastest safe systems ship additive minors behind enforced deprecations

The systems that change often without breaking consumers share a recognisable machinery. Its centrepiece is a published table that maps each kind of change to a semver bump. Primer's is the best primary source found. Adding a component is a minor, deprecating one is also a minor, and removing it is a major. Narrowing a prop type is a major. A change in how a component uses a CSS custom property is "potentially major", as is adding or removing a landmark role. Renaming or removing a `data-component` attribute is a major ([Primer versioning](https://github.com/primer/react/blob/main/contributor-docs/versioning.md)). That table is the most reusable artefact in this research for a headless, token-first system, because it already treats CSS variables, ARIA and data attributes as public API.

Cadence data shows what "fast" means in practice. Primer ships a minor every one to two weeks and was still on major 38 in October 2026. React Aria Components and Spectrum 2 release together every four to seven weeks. GOV.UK Frontend ships minors every three to eight weeks with betas and release candidates for larger ones. The shadcn CLI ships patches several times a week ([Primer releases](https://github.com/primer/react/releases); [React Spectrum releases](https://github.com/adobe/react-spectrum/releases); [GOV.UK Frontend releases](https://github.com/alphagov/govuk-frontend/releases); [shadcn releases](https://github.com/shadcn-ui/ui/releases)). Atlassian reports 58+ updates in 12 months ([Atlassian blog](https://www.atlassian.com/blog/ai-at-work/atlassian-design-system-building-the-context-engine-for-the-ai-era)). The shape is consistent. **Speed comes from additive minors, and breaking changes are batched into rare majors.** Changesets is the de facto tool: each change records its bump type and changelog line when it is written, and CI turns them into releases ([changesets](https://github.com/changesets/changesets/blob/main/docs/intro-to-using-changesets.md)).

Unstable work is kept outside the semver contract, not merely flagged in docs. Primer publishes experimental components as separately versioned packages ([Primer ADR-007](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-007-experimental-components.md)). Carbon ships `preview_` exports and feature flags. Its `enable-v12-*` flags are frozen, so a consumer who turns them all on before v12 should need no changes when upgrading ([Carbon release schedule](https://github.com/carbon-design-system/carbon/blob/main/docs/release-schedule.md); [Carbon feature flags](https://github.com/carbon-design-system/carbon/blob/main/docs/feature-flags.md)). GOV.UK uses a Trial status with a time-boxed exit: six months in trial with no negative feedback makes a component stable ([GOV.UK lifecycle](https://design-system.service.gov.uk/community/component-lifecycle-statuses/)).

Deprecation works through tooling, not warnings. Primer's ADR-019 sets the sequence: add a TypeScript `@deprecated` tag, mark it in docs, write an ESLint rule, measure impact in the main consumer, autofix where safe, then enable the rule so new uses are blocked. It explicitly **rejected console warnings** as "not as effective as the linting rule" ([Primer ADR-019](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-019-deprecating-props.md)). Atlassian pairs `no-deprecated-imports` with codemods and keeps deprecated packages on npm "in perpetuity" ([Atlassian ESLint](https://atlassian.design/components/eslint-plugin-design-system/no-deprecated-imports)).

The clearest "learn from your own mistakes" mechanism is the same flow applied to errors: a mistake becomes a lint rule or test, and the rule makes recurrence impossible. Primer keeps 26 numbered ADRs in its repo, each with separate Approved and Adopted statuses, and supersedes them explicitly ([Primer ADRs](https://github.com/primer/react/tree/main/contributor-docs/adrs)). Carbon only began ADRs in 2025, because "the context and reasoning surrounding many decisions has been lost" ([Carbon ADR-0001](https://github.com/carbon-design-system/carbon/blob/main/docs/decisions/0001-record-project-decisions.md)). Carbon's postmortem folder is the cautionary tale. It has a good template and a 2019 incident in which a hooks refactor changed a public `onChange` signature in a minor release. Yet only four postmortems exist, all from 2019 to 2020 ([Carbon postmortems](https://github.com/carbon-design-system/carbon/blob/main/docs/postmortems/README.md)). The inference is that **a mistakes log without a mandatory automated guard decays into a diary**. The research also found no public, maintained known-issues log from any major system, which is an open gap a personal system can fill.

Testing follows the same pattern of one harness. Primer's ADR-017 runs interaction tests by having Playwright visit Storybook stories, so the same harness serves visual regression and axe accessibility checks ([Primer ADR-017](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-017-interaction-tests-revisited.md)). ADR-011 bans "catch-all" snapshot tests but allows snapshots of static objects such as the package export list ([Primer ADR-011](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-011-snapshot-tests.md)). Carbon uses Jest and Playwright the same way ([Carbon testing](https://github.com/carbon-design-system/carbon/blob/main/docs/testing.md)). Automation's reach is debated. Deque's vendor study found axe caught **57% of issues by volume** across 13,000+ pages, far above the commonly cited 20 to 30%, because it counts issues rather than WCAG criteria ([Deque](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues)). Either way, a large share needs a human with a screen reader. GOV.UK requires components to be "tested across browsers, assistive technologies, and devices" and to state the contexts in which they were tested ([GOV.UK criteria](https://design-system.service.gov.uk/community/contribution-criteria/)).

Documentation that works is generated, not written twice. Primer's v38 migration table listed one entry for a release that removed whole APIs ([Primer migration guides](https://primer.style/product/getting-started/react/migration-guides)). The inference is to generate migration notes from deprecation metadata so they cannot fall behind. Carbon single-sources its feature-flag docs into Storybook pages, and its ADR-0005 requires realistic example content ([Carbon decisions](https://github.com/carbon-design-system/carbon/tree/main/docs/decisions)). The research found no primary source criticising missing "when not to use" sections. Its absence is a gap in the evidence, not proof that systems handle it well.

## Friendly to humans and agents means compiled context and deterministic gates

Shipping a machine interface is now table stakes. Kaelig Deloumeau-Prigent's July 2026 study of 21 major systems found that **18 ship an official MCP server, 18 ship agent skills and 15 publish llms.txt**, with installation converging on `npx skills add` ([State of AI in Design Systems](https://state-of-ai-in-design-systems.netlify.app/); [insights](https://state-of-ai-in-design-systems.netlify.app/insights.md)). Primer's `@primer/mcp` exposes 19 tools, including `lint_css` so an agent can check its own token usage ([Primer MCP](https://primer.style/product/getting-started/foundations/mcp/)). Atlassian's public CLI has a `--json` flag for agents ([Atlassian: Develop with AI](https://atlassian.design/get-started/develop/with-ai)). The competition has moved on to context budgets. Chakra slices its llms.txt six ways, while Mantine's single llms-full file reached megabytes ([insights](https://state-of-ai-in-design-systems.netlify.app/insights.md); [Chakra](https://chakra-ui.com/docs/get-started/ai/llms)).

The study's sharpest conclusion is that **"instruction hopes the model complies, while structure checks"**. The field has moved through three generations: docs reshaped for machines, then rules and skills, then structural coercion. The third includes tool-gating ("call this first"), CLI-only installs, and validators the agent must pass. Astryx keeps "no LLM in the enforcement path": its AI reviewer is advisory and the merge-blocking check is deterministic ([insights](https://state-of-ai-in-design-systems.netlify.app/insights.md)). A practitioner found that a standing "never invent props" instruction "raised the floor" but did not stop duplicate components ([rachel.fyi](https://rachel.fyi/posts/storybook-mcp-reads-your-manifest-not-your-docs-tab)). The same write-up found that **guidance written in Storybook's Docs tab never reached the agent-facing manifest**, so the agent could not tell which component to choose. Machine docs must come from structured fields, not prose that happens to render on a page.

The hard numbers are few, self-reported and sobering. Atlassian reports a 52% accuracy improvement and 16% fewer tokens from its structured AI context ([Atlassian blog](https://www.atlassian.com/blog/ai-at-work/atlassian-design-system-building-the-context-engine-for-the-ai-era)). Astryx publishes a nightly benchmark of agent-written UI against a shadcn and Tailwind baseline, and **the baseline won 50 of 91 nights** as of July 2026 ([insights](https://state-of-ai-in-design-systems.netlify.app/insights.md)). Storybook's own RFC states the problem: agents "often ignore a team's design system" and reach for shadcn and Tailwind, and LLM-generated docs were "inaccurate, inconsistent, and not exhaustive" ([Storybook RFC](https://github.com/storybookjs/ds-mcp-experiment-reshaped/discussions/1)). Agents favour shadcn partly because its source sits in the repo where they can read it, while a packaged library leaves the model to "see an import and guess" ([shadcn.io](https://www.shadcn.io/ui/why-ai-coding-tools-love-shadcn-ui); practitioner claim). Hallucinated props such as a `loading` prop on shadcn's Button, which has none, are the typical failure ([LogRocket](https://blog.logrocket.com/ai-shadcn-components/)). Ant Design's allow-list exists specifically to block invented `Box` and `Stack` imports ([insights](https://state-of-ai-in-design-systems.netlify.app/insights.md)).

On the designer side, Figma's MCP server now has write tools (`use_figma`, `generate_figma_design`) alongside `get_variable_defs` ([Figma MCP tools](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)). Code Connect, the official link between Figma components and code, is limited to Organization and Enterprise plans ([Figma Help](https://help.figma.com/hc/en-us/articles/23920389749655-Code-Connect)) and is barely used: only three of the 21 studied systems rely on it ([insights](https://state-of-ai-in-design-systems.netlify.app/insights.md)). Detached Figma instances are how accessibility fixes fail to reach design files, because a detached instance "misses out on critical updates" ([Salesforce](https://www.salesforce.com/blog/figma-component-health/)). Brad Frost's 2026 framing is that systems become machine-readable infrastructure, with AI "deliberately constrained" to their materials ([Brad Frost](https://bradfrost.com/blog/link/agentic-design-systems-in-2026-with-brad-frost/)). The person who decides which components exist and what they are called is still a designer ([Vallaure](https://christinevallaure.substack.com/p/agentic-ai-design-systems-and-figma)). For developers, the best 2026 patterns serve humans and agents equally: shadcn's `info`, `docs`, `--dry-run` and `--diff` commands ([shadcn CLI v4](https://ui.shadcn.com/docs/changelog/2026-03-cli-v4)), and Atlassian's observation that rules written to help LLMs also explain the system to people ([Atlassian blog](https://www.atlassian.com/blog/ai-at-work/atlassian-design-system-building-the-context-engine-for-the-ai-era)).

Putting this together, "friendly to both" has a concrete meaning (inference). Every fact about a component lives once, in a structured spec. Docs pages, TypeScript types, the agent manifest, the llms.txt slices and the Figma mirror are all compiled from that spec. Closed TypeScript unions make invented props fail type-checking. Token lint makes raw values fail CI. And the agent can run the same lint and tests itself before a human sees the change.

## Saral's decisions hold up, with five adjustments

The table checks each of the owner's decisions against the evidence. "Evidence" means a cited source above directly supports the verdict. "Inference" means the verdict is this report's reasoning from that evidence.

Two of these deserve emphasis. The first is the state machines. The owner's architecture is right for the system Saral will become, but the v1 kit barely needs it. A checkbox built on `<input type="checkbox">` gets keyboard handling, form participation and screen-reader semantics from the browser, and a hand-written machine can only add bugs. The evidence-backed role for the machine in v1 is narrower and more valuable. It should normalise interaction state into data attributes, because pseudo-classes misbehave on touch. It should own the field's validation and error lifecycle. And it should serve as the portable spec that a SwiftUI or Compose port will later be checked against. The second is the native outputs. Shipping Swift and Compose tokens costs little with an own build script. Promising them under semver, with no app compiling them, invites exactly the spec-versus-platform drift that Material Web shows. A CI job that compiles the generated Swift and Kotlin, plus a "preview" label, keeps the promise honest at near-zero cost (inference).

## Execution in five phases, each gated by what it must prove

The sequence below orders work so that each phase produces something the next one depends on, and so the personal website absorbs risk before any outside consumer does. The basis for each phase is marked.

**Phase 0: write the contract before the code.** Create `docs/decisions/` with Nygard-style ADRs carrying Primer's separate Approved and Adopted statuses, and record the decisions above as the first entries ([Primer ADRs](https://github.com/primer/react/tree/main/contributor-docs/adrs); evidence). Publish a change-type table modelled on Primer's and extended for tokens: a renamed or removed token is a major; a changed token value is a minor or patch depending on whether it is a declared design change; a renamed data attribute or changed ARIA role is a major ([Primer versioning](https://github.com/primer/react/blob/main/contributor-docs/versioning.md); evidence for the base table, inference for the token rows). Fix the attribute contract (`data-scope`, `data-part`, boolean states) and the cascade-layer order (reset, tokens, components, utilities, overrides), with component selectors wrapped in `:where()` for zero specificity. Spectrum 2's late layering and MUI's specificity increase are the evidence for doing this on day one ([React Spectrum](https://react-spectrum.adobe.com/migrating); [MUI](https://mui.com/material-ui/migration/migrating-from-jss/)). Define three stability tiers (preview, stable, deprecated) and a GOV.UK-style exit rule ([GOV.UK](https://design-system.service.gov.uk/community/component-lifecycle-statuses/)). Write a short `AGENTS.md` router that lists every real component and gives Incorrect and Correct pairs, following the Carbon and Cloudscape style ([insights](https://state-of-ai-in-design-systems.netlify.app/insights.md); evidence). The phase is done when the contract exists and an agent can read it.

**Phase 1: the token compiler and its gates.** Author DTCG 2025.10 with colours in OKLCH, a Resolver `theme` modifier for light and dark (and a high-contrast context, which is cheap), the width axis and springs in `$extensions` under Saral's own reverse-domain key, and a lean three-tier model whose component tier exists only where a component must deviate. The build script's gates are ranked by where the evidence says systems break (inference from the cited failures). It must resolve aliases and fail on cycles or dangling references. It must check that every semantic token exists in every mode, which mirrors Figma's silent drop. It must do OKLCH to sRGB gamut mapping in one deterministic place. It must run a WCAG 2.x contrast gate on the declared foreground and background pairs only, using resolved sRGB values, with APCA as a warning at most. It must enforce the one-accent rule and the deprecation lifecycle. And it must write snapshot diffs of every output, so that cross-platform changes show up in review. Outputs are CSS custom properties, JS, and a Tailwind v4 `@theme` preset as stable, plus Swift (an asset catalog, following Terrazzo's precedent), Compose and Figma-ready DTCG (sRGB hex, px, seconds, one file per mode) as preview, each compile-checked in CI ([Terrazzo](https://terrazzo.app/docs/integrations/swift/); [Figma Help](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)). Add a check that every fluid `clamp()` contains a rem term (evidence: [Roselli](https://adrianroselli.com/2019/12/responsive-type-and-zoom.html)). The website then adopts the tokens before any component. This is the lowest-risk proof that the pipeline works, and the phase exit is the site rendering identically on Saral tokens.

**Phase 2: the kit on native elements, with the one test harness.** Build button, link, checkbox, radio, field with error state, native select, tag, notice and card. Each gets a spec file that lists its parts, states, events, keyboard and ARIA contract, and a "when not to use" field. Write machines only for interaction normalisation and the field and error lifecycle. Keep the React adapter dumb: all timing, focus and validation logic lives in the core, which is the bug class Zag was built to escape ([Zag](https://zagjs.com/overview/introduction); evidence). Expose a `render` prop with the explicit ref-and-spread contract. Make every prop a closed TypeScript union. Wire one harness of fixture pages, Playwright and axe, with `toHaveScreenshot()` on the theme layer only, plus a snapshot of the public export surface ([Primer ADR-017](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-017-interaction-tests-revisited.md); [ADR-011](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-011-snapshot-tests.md); evidence). The export snapshot is the guard that would have caught Carbon's hidden API break (inference). Record a manual screen-reader pass per component with its date, starting with VoiceOver on macOS and iOS since that is the hardware at hand, and add NVDA with Firefox when possible ([QualiBooth](https://www.qualibooth.com/resources/screen-reader-testing-guide); secondary). Add a per-component size budget, following Shopify's enforced 64KB extension cap ([InfoQ](https://infoq.com/news/2026/10/shopify-web-components); evidence for the practice). Ship stylelint and ESLint rules that ban raw values outside the token set, following Atlassian's and Mozilla's token rules ([Atlassian](https://atlassian.design/components/eslint-plugin-design-system/ensure-design-token-usage); [Mozilla](https://firefox-source-docs.mozilla.org/code-quality/lint/linters/stylelint-plugin-mozilla/rules/use-design-tokens/color.html)). The website migrates component by component. A react-scanner run in its CI reports which Saral exports it uses, as Brevo did ([Brevo](https://engineering.brevo.com/how-to-track-design-system-adoption/)).

**Phase 3: compile the docs, agent and designer surfaces from the spec.** The docs site, built with Saral, renders each component's purpose, when not to use it, its anatomy and data attributes, its keyboard and ARIA contract, its screen-reader matrix with dates, props generated from types, live examples that are also test fixtures, its stability tier and a filtered changelog. The same structured fields compile to a small llms.txt index with per-component slices, markdown twins of every page, an agent skill with progressive disclosure, and a CLI with `--json` and `info`/`docs` commands that can later be wrapped as an MCP server. Every machine artefact is versioned with the package. This is the 2026 median for credible systems, and anything less ranks Saral below it ([insights](https://state-of-ai-in-design-systems.netlify.app/insights.md); evidence for the median, inference for the exact set). Generate the Figma mirror through the Plugin API or Figma's MCP write tools, with each variable's code syntax set to its Saral CSS variable name so `get_variable_defs` hands agents real names instead of hex (inference from [Figma MCP tools](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)). Add a CI drift check between Figma variables and the DTCG source.

**Phase 4: turn the learning loop and the speed claim into public proof.** Release with changesets whenever CI is green, with additive minors as the norm. Batch removals into rare majors, each preceded by a minor that adds `@deprecated`, a lint rule and a codemod that an agent applies to the website as a pull request before the major lands. That is Primer's ADR-019 flow made affordable by agents ([Primer ADR-019](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-019-deprecating-props.md); evidence plus inference). Keep `docs/incidents/` on Carbon's template, with one non-negotiable addition: **every incident must link to the automated guard that now prevents it**, or it stays open (inference from Carbon's lapse). Publish a small, fixed-prompt eval scoring agent output with Saral context, without it, and against a shadcn baseline using deterministic checks, and publish the losses as Astryx does ([insights](https://state-of-ai-in-design-systems.netlify.app/insights.md)). Track the metrics that matter for a one-consumer system (inference): regressions shipped per release, time from report to merged guard, the share of website UI built on Saral, accessibility checks passing with last manual-test dates, open deprecations and their age, and the website's upgrade lag. Stars and component counts are vanity metrics here.

**Phase 5: expand only when a real consumer asks.** Native components in SwiftUI or Compose, built against the spec's conformance list rather than ported code. Overlays built on `<dialog>`, the Popover API and `inert`, with `@floating-ui/dom` for positioning, rather than JavaScript body locks (inference from the Radix body-lock failure). Then combobox and other hard widgets, and other framework adapters. Each enters as preview and follows the trial-to-stable rule.

## Saral should refuse five races it cannot win

The ambition to be the fastest-evolving benchmark system conflicts with the evidence in specific, nameable ways, and saying so plainly protects the parts where Saral can lead. **Breadth is unwinnable.** Ark ships 45+ components across four frameworks and Base UI shipped 35 at 1.0, backed by teams that still missed their own dates by a year ([Ark UI](https://ark-ui.com/); [Base UI v1](https://app.unpkg.com/@base-ui/react@1.6.0/files/docs/react/overview/releases/v1-0-0.md)). **Hard widgets** (combobox, multi-select, date picker) are where even funded libraries lag, and Atlassian's old date picker confused screen readers by auto-opening on focus ([Atlassian blog](https://www.atlassian.com/blog/ai-at-work/atlassian-design-system-building-the-context-engine-for-the-ai-era)). **Release count** is a proxy that staffed teams win: Primer's weekly minors come from a team, and Atlassian's 58 updates a year from an organisation. **Multi-framework adapters and native component runtimes** multiply the surface that killed Fluent's parity and Polaris's goodwill. **MCP tool breadth and paid design-platform integrations** (Code Connect, Make kits on private registries) are plan-gated or organisation-scale investments, and the evidence says the cheap structured equivalents work. Finally, a public repo with a single maintainer carries the exact bus-factor risk that moved shadcn off Radix. The honest response is a stated support promise and status labels, not a claim to match a team.

What Saral can genuinely lead on is narrower and more interesting (inference). It can lead on the **tightest learning loop** in public: a maintained incident log where every entry links to its guard, which no major system was found to keep. It can lead on a **token-and-anatomy change table** that treats tokens, data attributes and ARIA as semver contract from v1. It can lead on a **public agent eval that includes losses**, as only Astryx and Atlassian do. And it can lead on **zero upgrade lag** for its one real consumer, achieved by agent-written codemod pull requests. "Fastest-evolving" then means the shortest time from a mistake to a merged rule, not the most releases. A one-person system can credibly win on that measure.

## Conclusion

The research reframes what a headless design system is for. The industry's expensive failures were rarely bad components. They were contracts that leaked: styling engines that turned out to be public API, internal markup that consumers had to reach into, defaults that shipped as-is to users and into model training data, and docs and Figma kits that described a system that no longer existed. The systems that recovered fastest did so by making the contract explicit and machine-checkable. That means change tables that cover CSS variables and ARIA, lint rules instead of warnings, frozen preview flags, and since 2025 compiled context for agents. That makes Saral's real product **a compiler from one neutral spec to every surface, with gates that refuse inconsistent output**. The components are the least novel part.

The second shift is that agents are now both the cheapest maintainer and the least reliable reader. They make Primer-grade deprecation flows, codemods and incident write-ups affordable for one person. Yet the best-equipped AI-native systems still lose to the shadcn median more often than not. For Saral this means its strongest guard against sameness is not its visual brand. It is a contract that agents cannot route around because it fails the build when they try. If Saral publishes that contract, the gates and the evidence of where they failed, it will be a benchmark that someone with a full-time job can actually maintain.
